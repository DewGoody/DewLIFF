01 — Overview
System Overview
Laan Kijjakam คือ platform สำหรับสร้าง LINE Activity Quiz Campaign แบบ config-driven ไม่ต้อง deploy code ใหม่ทุกครั้งที่เปลี่ยนแคมเปญ

เป้าหมายหลัก

  • Config-driven — ทุกอย่างควบคุมจาก JSON config ที่ admin ตั้งผ่าน UI
  • Multi-campaign — รองรับหลาย campaign_id ในระบบเดียว
  • Viral loop — Pair quiz + Group result ออกแบบมาเพื่อแชร์ใน LINE
  • Reward integration — แจก coupon code อัตโนมัติเมื่อถึง milestone

Use Cases หลัก

Use Caseตัวอย่างFeature ที่ใช้
Pair Quizโลกแตกพรุ่งนี้ เรารอดกี่วันPair mode + axis scoring
Group Resultกลุ่มเพื่อนรอดได้กี่วันGroup score mode
Destination Matchทีมนี้เหมาะเที่ยวไหนGroup match mode
Reward Campaignครบ 5 คู่ รับโค้ดส่วนลดMilestone + Reward pool

Roles ในระบบ

  • Campaign Admin — ตั้งค่า config ผ่าน Admin Console
  • End User — ตอบ quiz + ดูผลผ่าน LIFF ใน LINE
  • Developer — maintain backend API, deploy, ดู logs

CampaignConfig Schema
Schema นิยามด้วย Zod ที่ src/config/schema.ts — ใช้ทั้ง backend validation และ admin TypeScript types
CampaignConfig {
  campaign_id: string           // unique slug e.g. "buddy_demo"
  version: number               // auto-increment on save
  mode: "pair" | "solo" | "guess" | "mbti"

  axes: AxisDef[]               // แกนบุคลิก
  questions: Question[]         // คำถาม + ตัวเลือก
  results: ResultRule[]         // ผลลัพธ์คู่/solo
  fallback_result: string       // code ของ ResultRule ที่ใช้ fallback

  brand?: BrandConfig           // สี, ชื่อ, font
  copy?: Record<string,string>  // ข้อความทุกจุด
  rules?: RulesConfig           // invite TTL, max pairs/day
  messages?: MessagesConfig     // Flex Message templates
  rewards?: RewardsConfig       // milestones + pools
  group?: GroupConfig           // group result (optional)
  appearance?: AppearanceConfig // KV images, background
}

AxisDef

AxisDef {
  id: string              // slug e.g. "prep"
  label: string           // ชื่อที่โชว์ e.g. "สายเตรียมพร้อม"
  color: string           // hex color
  group_weight?: number   // น้ำหนักใน group score formula (0-100)
}

Question

Question {
  text: string
  options: QuestionOption[]
}

QuestionOption {
  label: string
  scores: Record<axisId, number>   // คะแนน +/- ต่อ axis
}

ResultRule

ResultRule {
  code: string              // slug e.g. "mu_x_prep"
  title: string             // ชื่อผลลัพธ์
  body: string              // คำอธิบาย
  image_url?: string
  pair?: [axisId, axisId]   // pair mode: คู่ axis นี้ได้ผลนี้
  score_contribution?: number  // group score mode: คะแนนที่คนนี้ให้กลุ่ม
}

GroupConfig

GroupConfig {
  enabled: boolean
  result_mode: "match" | "score"
  min_members: number         // เริ่มดูผลได้
  reward_members: number      // ถึงจุดนี้ถึงรับรางวัล
  max_members: number         // เกินนี้ → overflow
  overflow_mode: "hard_cap" | "rolling" | "creator_pick"
  batch_size?: number         // rolling mode: คนต่อ batch
  result_locks_at?: number    // ล็อคผลเมื่อถึง N คน
  archetypes: GroupArchetype[]
  fallback_archetype: string  // code ของ fallback
}

GroupArchetype {
  code: string
  title: string
  body: string
  image_url?: string
  min_group_size: number      // tier เริ่มแสดงผลนี้
  max_group_size?: number
  condition?: GroupCondition  // เงื่อนไข (match mode)
  min_score?: number          // ช่วงคะแนน (score mode)
  max_score?: number
  fallback?: boolean          // ผลสำรองเมื่อไม่มี match
  reward_pool_id?: string
}

GroupCondition {
  has_axes?: string[]         // ต้องมีคนสาย...
  has_mode?: "any" | "all"
  top_axes?: string[]         // axis ที่ครองเสียง
  top_n?: number
  is_balanced?: boolean       // กลุ่มสมดุล
  dominant_threshold?: number // % สำหรับ is_balanced
}

Backend แปลง CampaignConfig เป็น PublicConfig ก่อนส่งให้ LIFF เพื่อซ่อน field ที่ไม่ควรเห็น:

FieldCampaignConfigPublicConfig

Cache Busting

LIFF bundle ถูก cache โดย LINE WebView — ใช้ version.json + localStorage เพื่อ force reload เมื่อ version เปลี่ยน

// inline script ใน index.html ก่อน SDK โหลด
fetch('/version.json?_=' + Date.now(), { cache: 'no-store' })
  .then(r => r.json())
  .then(d => {
    const stored = localStorage.getItem('__lk_ver');
    if (stored && stored !== d.v) {
      localStorage.setItem('__lk_ver', d.v);
      location.reload(true);
    } else {
      localStorage.setItem('__lk_ver', d.v);
    }
  });
สำคัญ: ทุกครั้งที่ build LIFF ด้วย Vite — ต้องอัปเดต public/version.json ด้วยค่าใหม่ (เช่น {"v":"260821h"}) และ restore public/liff-app/index.html title + script เพราะ Vite จะเขียนทับ

Pair Quiz Flow
flow หลักของ platform — คน A ชวนคน B มาตอบแล้วดูผลร่วมกัน
1
คน A เปิด LIFF
GET /api/config/:id → โหลด CampaignConfig → แสดงหน้า Intro
2
A ตอบ quiz
บันทึก answers ใน state → POST /api/answers → ได้ axis_scores + archetype → บันทึกลง quiz_answers
3
A สร้าง invite
POST /api/pair/create → ได้ invite token → แชร์ลิงก์ /?token=xxx ผ่าน LINE Flex Message
4
คน B เปิดลิงก์
LIFF ตรวจ token → แสดงชื่อ A + ปุ่ม "ตอบเลย" → B ตอบ quiz → POST /api/answers
5
คำนวณผลคู่
ดู axis dominant ของ A และ B → หา ResultRule ที่ pair match → บันทึกลง pair_results
6
Push notification ไปหา A
LINE Messaging API ส่ง Flex Message แจ้งว่า "B ตอบแล้ว มาดูผลกัน"
7
ดูผลคู่
A และ B เปิด LIFF → GET /api/pair/:token → แสดง PairResult screen

Axis Scoring Algorithm

// 1. รวมคะแนนตาม option ที่เลือก
axis_scores = {}
for each answer:
  for each (axisId, score) in option.scores:
    axis_scores[axisId] += score

// 2. หา dominant axis (highest score)
dominant = max(axis_scores)

// 3. หา ResultRule ที่ pair ตรง
result = results.find(r => r.pair includes [A.dominant, B.dominant])
       ?? fallback_result

Group Result System
ระบบดูผลลัพธ์แบบกลุ่ม สำหรับ viral sharing ใน LINE

สองโหมด

Modeวิธีเลือกผลตัวอย่าง
matchดู axis composition ของกลุ่ม → เปรียบ GroupCondition → เลือก archetype ที่ matchกลุ่มนี้เหมาะเที่ยวบาหลี
scoresum(score_contribution ของทุกคน) → เทียบ min_score/max_score → เลือก tierกลุ่มนี้รอดได้ 40 วัน

Group Evaluation Algorithm (match mode)

function evaluateArchetype(members, archetypes, groupSize):
  // เรียง archetype: min_group_size desc (เจาะจงสุดขึ้นก่อน)
  eligible = archetypes
    .filter(a => a.min_group_size <= groupSize)
    .filter(a => !a.max_group_size || a.max_group_size >= groupSize)
    .sort((a,b) => b.min_group_size - a.min_group_size)

  // หา non-fallback ที่ match ก่อน
  for arch in eligible.filter(a => !a.fallback):
    if matchesCondition(members, arch.condition):
      return arch

  // ถ้าไม่มี → ใช้ fallback
  return eligible.find(a => a.fallback)

function matchesCondition(members, condition):
  if condition.has_axes:
    axisPresentInGroup = members.map(m => m.dominant_axis)
    if mode == "any": return condition.has_axes.some(a => axisPresentInGroup.includes(a))
    if mode == "all": return condition.has_axes.every(a => axisPresentInGroup.includes(a))

  if condition.top_axes:
    groupAxisScores = sum(member.axis_scores) for each axis
    topAxis = max(groupAxisScores)
    return condition.top_axes.includes(topAxis)

  if condition.is_balanced:
    maxShare = max(axis%) across all axes
    return maxShare < condition.dominant_threshold (default 0.5)

Group Score Algorithm (score mode)

groupScore = sum(member.archetype.score_contribution for each member)
// score_contribution ตั้งใน Step 3 → ResultRule.score_contribution

result = archetypes
  .filter(a => !a.min_score || groupScore >= a.min_score)
  .filter(a => !a.max_score || groupScore <= a.max_score)
  .find(a => !a.fallback) ?? fallbackArchetype

Overflow Modes

Modeพฤติกรรม
hard_capเมื่อกลุ่มเต็ม (= max_members) คนใหม่ join ไม่ได้
rollingทุก batch_size คน = 1 batch ใหม่ แต่ละ batch claim reward ได้อิสระ

Claim Flow (Race-condition Safe)

POST /api/group/:id/claim

1. ตรวจ group status + member count >= reward_members
2. ตรวจ member ยังไม่เคย claim
3. BEGIN TRANSACTION
   a. SELECT code FROM reward_codes
      WHERE pool_id = ? AND claimed = false
      LIMIT 1 FOR UPDATE SKIP LOCKED
   b. UPDATE reward_codes SET claimed = true, claimed_by = userId
   c. INSERT INTO reward_claims (...)
   d. UPDATE group_members SET reward_claimed = true WHERE user_id = userId
4. COMMIT
5. Return { code }
Race condition: ใช้ FOR UPDATE SKIP LOCKED ป้องกันสองคนได้โค้ดเดียวกันพร้อมกัน

State Management

ทั้งหมดอยู่ใน App.tsx — ไม่ใช้ global state library

State ใน App.tsx:
  screen: Screen           // current screen
  config: AppConfig        // campaign config จาก API
  myUserId: string         // จาก liff.getProfile()
  groupId: string          // pending group join
  answers: number[][]      // คำตอบก่อน submit
  archetype: string        // ผล archetype ของตัวเอง
  pairs: PairEntry[]       // pair log
